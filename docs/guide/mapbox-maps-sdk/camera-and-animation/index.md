# Swift로 이해하는 Mapbox 카메라와 애니메이션

> **면접 답변 한 줄 요약:** 지도 카메라는 지도를 바라보는 위치와 방향을 정하고, 애니메이션은 이동 과정을, Viewport는 지속적인 카메라 제어 의도를 표현해요.

공식 [Camera and Animations](https://docs.mapbox.com/ios/maps/guides/camera-and-animation/)에 대응하는 학습 진입점이에요. 아래 분류와 적용 순서는 검색·길찾기 화면을 설계할 때 사용할 수 있도록 구성한 학습용 기준이에요.

## 먼저 알아둘 용어

| 용어       | 쉬운 뜻                                                                      |
| ---------- | ---------------------------------------------------------------------------- |
| 카메라     | 지도 중 어느 곳을 어떤 각도와 배율로 보여줄지 정하는 가상의 시점이에요.      |
| 애니메이션 | 시작한 화면과 목표 화면 사이를 시간에 따라 연결하는 움직임이에요.            |
| Viewport   | 한 번 정한 숫자 대신 사용자 추적 같은 카메라의 동작 목표를 표현하는 API예요. |

## 기능 이름보다 화면의 의도를 먼저 정해요

“지도를 이동한다”라는 요구만으로 구현을 시작하면 검색 결과 선택과 사용자 추적이 같은 함수에 섞이기 쉬워요. 먼저 다음 질문으로 구분해 보세요.

| 사용자 의도                   | 먼저 읽을 문서                | 앱이 보관할 값                        |
| ----------------------------- | ----------------------------- | ------------------------------------- |
| 이 장소를 보여줘요            | [카메라 위치](./camera.md)    | 선택한 장소와 좌표                    |
| 이동한 방향을 이해하고 싶어요 | [애니메이션](./animations.md) | 목표 장소와 전환 완료 정책            |
| 이동하는 나를 따라와요        | [Viewport](./viewport.md)     | 추적 중인지 탐색 중인지 나타내는 상태 |

예를 들어 지도에 표시할 목적지만 정해졌다면 장소 선택 모델에 애니메이션 객체까지 넣을 필요는 없어요. 먼저 순수한 사용자 의도를 정의할 수 있어요.

```swift
enum MapFocusIntent: Equatable {
    case browse
    case selectedPlace(id: String)
    case followUser
}
```

이 타입은 Mapbox API가 아닌 학습용 앱 모델이에요. `.selectedPlace`의 좌표 조회, `.followUser`의 권한 확인, 화면의 전환 효과는 각각 별도 단계에서 처리해요. 덕분에 지도 없이도 “검색 결과를 누르면 추적에서 장소 선택으로 바뀐다”를 검증할 수 있어요.

## 한 시점의 카메라 제어 주체를 정해요

다음 흐름은 카메라 명령이 서로 덮어쓰는 문제를 예방하기 위한 설계 예시예요.

```text
사용자 의도 → 화면 상태 → 하나의 카메라 제어 경로
                           ├─ 장소 선택: 목표 좌표로 이동
                           ├─ 내 위치: 추적 시작
                           └─ 지도 탐색: 자동 추적 중단
```

좌표가 바뀔 때마다 카메라를 갱신하는 코드와 검색 결과로 이동하는 코드가 동시에 실행되는지 확인해 보세요. 눈에 보이는 흔들림을 애니메이션 시간만 바꿔 해결하려 하면 실제 원인인 제어권 충돌을 놓칠 수 있어요.

## 적용 순서를 정리해요

1. 장소 선택, 경로 전체 보기, 내 위치 추적을 별도 요구로 적어요.
2. 각 요구가 일회성 이동인지 지속 상태인지 구분해요.
3. 카메라 숫자를 계산하는 코드와 사용자 의도 모델을 분리해요.
4. 연속 선택·사용자 드래그·화면 종료 때의 동작을 정해요.
5. 마지막 명령이 이기는지, 취소된 명령이 되살아나지 않는지 확인해요.

## 면접에서 이어질 수 있는 질문

### 카메라와 애니메이션은 왜 나누나요?

목표 화면과 이동 과정은 다른 결정이기 때문이에요. 같은 목적지라도 화면 진입은 즉시 표시하고 사용자 선택은 부드럽게 이동하도록 정할 수 있어요.

### 모든 이동에 Viewport를 직접 구현해야 하나요?

아니요. 먼저 제공되는 상태와 단순한 카메라 설정으로 요구가 충족되는지 확인해요. 직접 구현하는 상태가 많아질수록 제어권과 종료 조건도 늘어나요.

### 지도 없이 어떤 것을 테스트할 수 있나요?

사용자 의도가 어떤 화면 상태를 만드는지 테스트할 수 있어요. 실제 지도에서의 크기·가림·애니메이션은 별도 화면 검증이 필요해요.
