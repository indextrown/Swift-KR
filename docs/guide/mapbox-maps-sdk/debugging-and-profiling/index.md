# Mapbox 디버깅과 성능 분석 시작하기

> **면접 답변 한 줄 요약:** 지도 디버깅은 문제를 같은 조건으로 재현하고, 시각적 원인과 시간·자원 사용을 나누어 관찰해 변경 효과를 확인하는 과정이에요.

“지도가 느려요”만으로는 타일 요청이 느린지, 화면을 그리는 일이 많은지, 앱 상태 갱신이 과한지 알 수 없어요. 이 페이지는 공식 **Debugging and Profiling** 페이지에 대응하며, 네 도구 중 무엇부터 쓸지 정하는 시작점이에요.

## 먼저 알아둘 용어

| 용어      | 쉬운 뜻                                                   |
| --------- | --------------------------------------------------------- |
| 재현      | 문제가 발생한 조건과 동작을 다시 실행하는 일이에요.       |
| Profiling | 실행 시간과 자원 사용을 측정해 병목을 찾는 작업이에요.    |
| 회귀      | 변경 후 이전보다 동작이나 성능이 나빠진 상태예요.         |
| Signpost  | 실행 중 특정 사건과 구간에 남기는 성능 분석용 표식이에요. |

Mapbox v11의 분석 도구는 지도 호출을 기록하는 `MapRecorder`, 렌더링 통계와 추적 기능을 연결할 수 있어요. 공식 개요는 재현 가능한 카메라·스타일 조건에서 프레임 단위 문제를 조사하는 흐름을 소개해요. [공식 디버깅 개요](https://docs.mapbox.com/ios/maps/guides/debugging-and-profiling/)

## 지금 답할 질문으로 도구를 선택해요

다음은 작성자가 정리한 조사 순서예요. 모든 도구를 동시에 켜라는 뜻은 아니에요.

| 질문                                | 첫 도구                             | 다음에 할 일                             |
| ----------------------------------- | ----------------------------------- | ---------------------------------------- |
| 라벨이 왜 사라지나요?               | [디버그 옵션](./debug-options.md)   | 충돌·카메라·타일 경계를 분리해 확인해요. |
| 특정 이동에서만 깨지나요?           | [MapRecorder](./map-recorder.md)    | 같은 이동을 재생할 수 있게 만들어요.     |
| 레이어를 추가한 뒤 비용이 늘었나요? | [성능 통계](./performance-stats.md) | 같은 입력의 변경 전후를 비교해요.        |
| 느린 구간에서 어떤 작업이 겹치나요? | [Tracing](./tracing.md)             | Instruments 시간축에서 사건을 연결해요.  |

## 재현 입력과 측정 결과를 별도로 보관해요

```text
기기·SDK·스타일 버전 + 같은 카메라 동작
                        │
                        ▼
                  재현 가능한 실행
                 ┌──────┴──────┐
                 ▼             ▼
             시각적 관찰     시간·자원 측정
                 └──────┬──────┘
                        ▼
             한 가지 변경 후 다시 실행
```

예를 들어 핀 라벨 추가 전후를 비교하면서 카메라 확대 수준까지 바꾸면 어느 변경이 원인인지 알기 어려워요. SDK 버전, 지도 스타일, 기기, 네트워크·캐시 상태를 기록한 뒤 조사할 변수 하나만 바꾸세요.

## “빠르다”는 판정을 먼저 정의해요

산책 앱을 위한 작성자 예시는 다음과 같아요.

- 지도 첫 표시가 늦으면 첫 진입 시간을 따로 재요.
- 지도를 움직일 때 끊기면 같은 이동 구간을 반복해요.
- 화면을 여러 번 열수록 무거워지면 진입·종료 반복을 조사해요.
- 특정 지역에서만 느리면 동일 지역·동일 확대 수준으로 비교해요.

하나의 평균값으로 네 문제를 모두 평가하지 마세요. 분석 도구의 오버헤드도 있으므로 최종 사용자 체감은 진단 기능을 끈 구성에서도 확인해야 해요.

## 조사 체크리스트

- [ ] 문제를 한 문장과 하나의 재현 절차로 설명할 수 있나요?
- [ ] 기기·SDK·스타일 버전과 네트워크 조건이 남아 있나요?
- [ ] 원인 확인용 실행과 최종 성능 확인용 실행을 나눴나요?
- [ ] 변경 전후에 같은 입력과 같은 수집 조건을 사용했나요?
- [ ] 실험용 기능과 기록 데이터가 출시 경로에 남지 않나요?

## 면접에서 이어질 수 있는 질문

### 화면 녹화와 MapRecorder는 같은가요?

아니에요. 영상은 보이는 결과를 보여 주고, MapRecorder는 지도 API 동작을 재현하는 데 도움을 줘요. 두 자료는 조사에서 서로 다른 질문에 답해요.

### 통계만 보면 원인을 찾을 수 있나요?

비용 증가를 발견하는 데는 도움이 되지만 원인을 확정하지는 못해요. 재현 입력을 고정하고 스타일·데이터·앱 작업을 하나씩 바꾸는 실험이 필요해요.

### 왜 진단 기능을 끈 실행도 필요한가요?

측정 자체가 실행 조건에 영향을 줄 수 있기 때문이에요. 진단 중 발견한 개선이 실제 배포 구성에서도 유지되는지 확인해야 해요.
